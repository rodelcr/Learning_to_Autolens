## 2. The nbconvert rendering bug (Mod 03 c17, Mod 03 c19, Mod 06 c14)

### Symptom

These cells render fit-subplot residuals with visible ring/arc structure and
max |res| ~25σ, max χ² ~600–765.

### Evidence the fits themselves are correct

- The auto-saved `output/.../image/subplot_fit.png` (written by autolens when
  the fit finishes) shows clean 5.73σ residuals, χ² peak 32.81. This is the
  ground truth of the fit quality.
- A standalone Python reproduction of the notebook code (same dataset, same
  model, same priors, same Nautilus cache) produces max |res| = 5.73σ via
  `result.max_log_likelihood_fit` — **correct**.
- `Solutions/08 cell 9` consumes the same Mod 03 `result.max_log_likelihood_fit`
  path and renders correctly (5.73σ).
- `result.info` in the affected cells shows the correct best-fit parameters
  (e.g. Mod 03: θ_E = 1.600, ell_comps = (0.053, -0.001), gamma = (0.050, 0.050)).

### Root-cause hypothesis (unresolved)

The bug surfaces only inside `jupyter nbconvert --execute` for notebooks with
specific accumulated state. The same line of code
(`aplt.subplot_fit_imaging(fit=result.max_log_likelihood_fit)`) produces
different residual values under nbconvert vs. a standalone Python script with
identical inputs. This points to a JAX-state / matplotlib-figure-state /
autolens-analysis-caching interaction in 2026.4.13.6 that mutates the fit's
internal representation between execution of the fit cell and the
visualization cell.

### Workaround options (not yet applied)

1. Replace each broken `aplt.subplot_fit_imaging(...)` call with
   `IPython.display.Image(filename=".../image/subplot_fit.png")` — loads the
   known-good cached render. Bypasses the bug completely. **Recommended**.
2. Reconstruct the fit manually via `analysis.fit_from(instance=result.instance)`
   inside the affected cell. Does not bypass the bug in our testing.
3. Re-execute the notebook *interactively* (open in Jupyter, Run All) rather
   than via nbconvert. Reader-facing but the committed `.ipynb` would still
   contain the broken outputs.

### What this does NOT affect

- The committed Mod 04 / Mod 09 `results/` trees on disk (produced on Cannon
  at fit time, never round-tripped through notebook rendering).
- The PROGRESS_LOG audit table's reported χ²/N and max |res| values — those
  come from `export_results.py` reading `image/fit.fits` directly, not from
  notebook-rendered images.
- Any user who re-runs a fit on their own machine and examines the output
  directly.

```bash

bash Modules/10_Cluster_Computing/scripts/submit_to_cannon.sh 04

# When the sbatch email lands:
```

The submit wrapper pushes the repo, SHA256-verifies `fit_module${MODULE}.py`
on Cannon against the local copy, and only then calls `sbatch` with the
`cannon.env`-derived `--account / --partition / --mem / --mail-user` flags.
`export_results.py` runs as the post-fit step in the slurm script,
producing the lightweight `results/<stage>/` artifacts that the module
notebook loader cells consume.
