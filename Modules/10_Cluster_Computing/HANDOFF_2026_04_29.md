## 11. GPU acceleration investigation (commits `f0e2673`, `a370a24`, `c631e65`)

The user's question — "go back and read the docs and see why GPU
acceleration was implemented in the first place" — was a productive
push-back. Initial conclusion ("JAX-GPU is 5.5× slower than numpy") was
based on the **wrong metric**: single-call latency, when Nautilus
actually uses `use_jax_vmap=True` to batch proposals through
`jax.vmap(jax.jit(...))`.

**Per-call probe (Cannon job 9252282, mock_3 R5 with Iso masses):**

| Backend | Per-call | vs numpy single-thread |
|---|---|---|
| numpy serial | 95.6 ms | 1.0× |
| numpy 32-core mp (production) | ~3 ms effective | ~32× |
| JAX-GPU `FitImaging(xp=jnp)` direct | 510 ms | 0.19× |
| JAX-GPU `AnalysisImaging(use_jax=True)` | 1023 ms | 0.09× |
| **JAX-GPU `Fitness._vmap` batch=256** | **0.11 ms** | **~900×** |

The vmap'd batch path showed ~28× speedup vs numpy 32-core. Matched the
autoconf docs' "PyAutoLens runs >50× faster with GPU" claim.

**End-to-end head-to-head (jobs 9252945 vs 9252946, R5_truth_iso mock_3):**

| Wall time | CPU calls | GPU calls | Verdict |
|---|---|---|---|
| 1 min | 2,050 | 550 | GPU 4× SLOWER (JIT warm-up) |
| 12 min | 77,750 | 87,150 | GPU 12% faster |
| 1h 54m | (still running) | (still running) | TBD |

**Both jobs still running — final wall-time comparison will land in
the next session.** The 800× per-call vmap speedup did NOT carry through
to the actual fit. Reasons:

1. Nautilus's `n_batch=50` is much smaller than the probe's batch=256
   (sub-linear scaling means smaller batches lose the per-call win)
2. State-update overhead between batches (Python bookkeeping, prior
   remapping, result deserialization) is the same for CPU and GPU
3. JAX appears to recompile at each new bound network transition,
   visible in logs as ~5s pauses every 1-2 minutes

**Bottom line:** at our 9k pixel / multi-plane R5 scale, JAX-GPU offers
maybe 10-20% end-to-end speedup over numpy 32-core. Not worth the
operational complexity (PowerLaw JAX bug, JIT warm-up, GPU node
contention, --gres=gpu:1 limit) for a 13h → ~10h fit.

**The PyAutoLens "50× speedup" applies to**:
- Larger problem sizes (real HST 100k+ pixel cutouts)
- Pixelized sources with fine meshes (the inversion is GPU-friendly)
- Interferometer NUFFT operators (where they explicitly use sparse_operator)
- Operating points where compute >> Nautilus state-management overhead

Not our compound-mock multi-plane R5 fit operating point.

**Bug to file upstream:** autolens 2026.4.13.6's PowerLaw mass profile
JAX path crashes — `omega()` in
`autogalaxy/profiles/mass/total/jax_utils.py:41` passes `functools.partial`
to `jax.lax.scan`. Isothermal works fine. Probe falls back to Iso via
`PROBE_USE_POWERLAW=0` (default).

**Multi-GPU pmap status:** not tested, not justified by current data.
With single-GPU vmap giving only ~12% wall-time win, multi-GPU would
need to multiply across pmap-aware code that doesn't exist in autolens
out of the box. Deferred. The relevant memory is
`feedback_truth_anchored_validation.md` and
`project_multigpu_jax_idea.md` (updated with corrected understanding).
